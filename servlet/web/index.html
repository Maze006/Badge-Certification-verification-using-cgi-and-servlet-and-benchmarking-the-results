One lookup, built two ways

Students earn skill badges for completing course modules. Every badge carries a verification code that anyone can check without an account. The verification lookup is implemented twice — once as a CGI script, once as a Java servlet — and benchmarked against itself.

Student wallet

Browse students, see the badges they hold, and issue a badge for a completed module.

Verify a badge

The public, employer-facing check. Paste a code and get back the badge it belongs to, from either implementation.

Servlet health

Connection-pool statistics. Reload a few times and watch borrows climb while the pool size never moves.

The two implementations

EndpointServed byModel
/badgeportal/api/verify Apache Tomcatport 8080 One JVM, a pool of worker threads, a pool of live JDBC connections. Nothing is created per request.
/cgi-bin/verify.py Apache HTTP Servermod_cgi, port 80 A brand-new python.exe process per request, which must import its libraries and open its own database connection before it can answer, then exits.

Bars are drawn to scale, which is why the servlet is barely a sliver. Both endpoints answer the same question with the same SQL against the same indexed table, so the difference is the request lifecycle and nothing else. The servlet is 162× faster, and only 0.10% of a CGI request is the database lookup itself — the rest is setup the process throws away on exit.

Reproducing the benchmark

from the project root

python bench\benchmark.py --requests 100 --levels 1,2,5,10,20,40
python bench\cgi_cost_breakdown.py

Writes bench/results.csv, bench/chart.png and a markdown results table. Before timing anything it asserts that the two implementations return identical JSON — every field but the two that name the implementation and report its own timing. If they ever drifted apart the comparison would not be fair, so the benchmark refuses to run.
