# Verified Digital Skill-Badge Portal

**PBL 3 — CGI vs Servlet Benchmark**

Students earn micro-credential badges for completing course modules. Every badge
carries a tamper-evident verification code that anyone — an employer, say — can
check without an account.

The verification lookup is built **twice**: once as a Python CGI script under
Apache HTTP Server, once as a Java Servlet on Apache Tomcat. Both answer the same
question with the same SQL and return byte-identical JSON, so timing them against
each other isolates one variable: the request lifecycle.

The servlet answers the same lookup **269× faster** and sustains **73× the
throughput**. Pushed to 40 concurrent clients, CGI does not merely plateau — its
throughput *halves* while p95 reaches 4.07 seconds. Full numbers in
[REPORT.md](REPORT.md), and the mechanism behind them in
[docs/EXPLAINED.md](docs/EXPLAINED.md).

### Where the deployed copies land

`scripts\deploy.bat` does not serve the project folder directly. It copies into
the two servers:

| Source | Deployed to |
|---|---|
| `servlet/web/` + compiled classes | `C:\xampp\tomcat\webapps\badgeportal\` |
| `cgi/*.py` + `config/*.properties` | `C:\xampp\cgi-bin\` |
| MySQL driver, vendored for CGI | `C:\xampp\cgi-bin\pylib\` |

Editing a file under `servlet/web/` therefore has no effect until you redeploy.
And because Tomcat is not configured as `reloadable`, **editing any `.java`
needs a Tomcat restart, not just a redeploy** — CSS and HTML changes only need
the redeploy.

## Database structure

Schema `badgeportal` on `localhost:3306`. Created by `sql/01_schema.sql`,
populated by `sql/02_seed.sql`.

```
   accounts ───── login identity (ADMIN or STUDENT)
       │
       ▼
   students ──────┐                    ┌────── modules
  student_id      │                    │      module_id
       │          ▼                    ▼
       │  module_completions ─── proof the work was done
       │          │
       ▼          │
 badge_claims     │   a REQUEST, not a credential.
       │          │   no verification code until an admin approves.
       ▼          ▼
          badges ────────────── the credential itself
                               verification_code is what the
                               public endpoints look up
```

Two paths lead to a badge. A completed module can be issued directly, or a
student submits a claim for something earned elsewhere and an admin approves it.
Either way the badge is minted by the server, never by the student.

### `students` — 60 rows

| Column | Type | Notes |
|---|---|---|
| `student_id` | `int` | primary key, auto-increment |
| `name` | `varchar(100)` | |
| `email` | `varchar(150)` | unique |
| `enrolled_on` | `date` | defaults to the current date |

### `modules` — 6 rows

| Column | Type | Notes |
|---|---|---|
| `module_id` | `int` | primary key, auto-increment |
| `title` | `varchar(120)` | unique |
| `unit` | `varchar(60)` | e.g. `Unit 3 - Server-Side Java` |
| `code_prefix` | `char(2)` | the two-letter stem of the verification code, so `Servlet Fundamentals` produces codes beginning `SF-` |

### `module_completions` — 336 rows

| Column | Type | Notes |
|---|---|---|
| `completion_id` | `int` | primary key, auto-increment |
| `student_id` | `int` | FK to `students`, cascade delete |
| `module_id` | `int` | FK to `modules`, cascade delete |
| `score` | `decimal(5,2)` | 0–100, checked; drives the badge tier |
| `completed_at` | `datetime(3)` | |

Unique on `(student_id, module_id)` — a module is completed once.

This table is not in the original brief but is necessary: a badge is evidence
that work was completed, so without a completion record there is nothing for
issuance to verify, and the score that decides the tier has nowhere to live.
`IssueServlet` returns `NOT_COMPLETED` if no row here matches.

### `badges` — 336 rows

The table both verification endpoints read.

| Column | Type | Notes |
|---|---|---|
| `badge_id` | `int` | primary key, auto-increment |
| `student_id` | `int` | FK to `students` |
| `module_id` | `int` NULL | FK to `modules`; `NULL` for claim-issued badges |
| `verification_code` | `varchar(20)` | **unique** — e.g. `SF-DDDF-2864-66C7` |
| `tier` | `enum` | `BRONZE` / `SILVER` / `GOLD` |
| `score` | `decimal(5,2)` | copied from the completion at issue time |
| `issued_at_ms` | `bigint` | the canonical issue timestamp, and the value fed into the hash |
| `issued_at` | `datetime(3)` | the same instant, for display |
| `revoked` | `tinyint(1)` | `0` or `1` |
| `claim_id` | `int` NULL | FK to `badge_claims` when the badge came from a claim |
| `source` | `enum` | `MODULE_COMPLETION` / `ADMIN_APPROVED` |

Unique on `(student_id, module_id)` as well, which is what makes issuance
idempotent at the database level rather than only in application code. Because
SQL treats `NULL`s as distinct in a unique index, this still permits a student to
hold many claim-issued badges (all with `module_id IS NULL`) while remaining
limited to one badge per actual module.

Three design decisions worth knowing:

**The unique index on `verification_code`** is what makes the lookup an index
probe rather than a table scan — in *both* implementations. Without it the
benchmark would partly be measuring MySQL scanning rows, which is not the
difference it is meant to isolate.

**`issued_at_ms` exists alongside `issued_at`** because the millisecond value is
what gets hashed. Storing it as a plain integer means Java and Python derive
byte-identical digests, with no timezone conversion or fractional-second
rounding drifting between the two runtimes.

**`score` is duplicated onto the badge** rather than read back through the
completion. A credential should record what was true when it was issued; later
edits to a completion must not silently restate an already-issued badge.

### `accounts` — 6 rows

Login identities, added by `sql/03_accounts_and_claims.sql`.

| Column | Type | Notes |
|---|---|---|
| `account_id` | `int` | primary key |
| `email` | `varchar(150)` | **unique across the whole table** — one email is one account with one password |
| `password_hash` | `varchar(255)` | `pbkdf2_sha256$120000$salt$key`, self-describing |
| `role` | `enum` | `ADMIN` / `STUDENT` — an identity is one or the other, never both |
| `student_id` | `int` NULL | FK, unique; `NULL` for admins |
| `is_active` | `tinyint(1)` | soft disable |
| `created_at` / `last_login_at` | `datetime(3)` | |

A `CHECK` constraint enforces that admins have no `student_id` and students must
have one — the database refuses a malformed account rather than trusting
application code to remember.

Deliberately separate from `students`: a student is a person the institution
knows about; an account is a way to log in. 54 of the 60 seeded students have no
account at all, which is realistic.

### `badge_claims` — 4 pending

A student's request for a badge earned outside the course modules.

| Column | Type | Notes |
|---|---|---|
| `claim_id` | `int` | primary key |
| `student_id` | `int` | FK |
| `title`, `issuer` | `varchar` | e.g. "Python for Everybody", "Coursera" |
| `external_url` | `varchar(500)` | the link the student supplies |
| `evidence_path` / `evidence_name` | `varchar` | uploaded file |
| `proposed_tier` | `enum` | what the student asks for |
| `status` | `enum` | `PENDING` / `APPROVED` / `REJECTED` |
| `submitted_at` | `datetime(3)` | |
| `reviewed_by` / `reviewed_at` / `review_note` | | the audit trail |

**A claim is a request, never a credential.** It carries no verification code and
is invisible to `/api/verify`. Only when an admin approves does a row appear in
`badges` with a server-generated code. Keeping them in separate tables makes that
distinction structural rather than a flag somebody has to remember to check — and
it is what stops a student awarding themselves a credential.

### Getting a SQL prompt

In PowerShell, note the leading `&` — a quoted path at the start of a line is
otherwise treated as a string rather than a command to run:

```bash
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u root -p badgeportal
```

At the `mysql>` prompt only SQL is accepted, and every statement ends with a
semicolon. `\c` cancels a half-typed statement, `exit` returns you to the shell.

```sql
SELECT b.verification_code, s.name, m.title, b.tier
FROM badges b
JOIN students s USING (student_id)
JOIN modules  m USING (module_id)
LIMIT 10;
```

Note that XAMPP's phpMyAdmin is preconfigured for `root` with an empty password,
which will not authenticate against a root account that has one. Port 3306 here
is held by a standalone MySQL install rather than XAMPP's bundled one, which is
why the default XAMPP credentials do not fit. Either use the command line above,
or set the password in `C:\xampp\phpMyAdmin\config.inc.php`.

## What runs where

| | Servlet | CGI |
|---|---|---|
| Server | Apache Tomcat 8.5.96, port 8080 | Apache HTTP Server 2.4.58 + mod_cgi, port 80 |
| Verification endpoint | `/badgeportal/api/verify?code=…` | `/cgi-bin/verify.py?code=…` |
| Per request | a pooled thread, a pooled JDBC connection | a new `python.exe`, a new DB connection |

The servlet also serves badge issuance, the student wallet and the public verify
page. Only the **verification lookup** exists in both — that is what the PBL asks
to benchmark, and it mirrors how real credentialing platforms are shaped:
issuance is low-volume and transactional, verification is the high-volume public
path.

## Verification codes

A code looks like `JS-3986-8312-B276`: a two-letter module prefix, then twelve hex
digits of a SHA-256 digest in three groups of four.

```
code = prefix + first 12 hex of SHA-256(studentId : moduleId : issuedAtMillis : secret)
```

Because the badge row stores `student_id`, `module_id` and `issued_at_ms`, the
verifier **recomputes** the code the row should carry and compares it with the one
stored. Editing the database to point a valid-looking code at a different student
produces a digest mismatch, and the lookup returns `TAMPERED` instead of `VALID`.
That is what "tamper-evident" means here — not that the database cannot be edited,
but that edits cannot go unnoticed without the signing secret.

The algorithm exists twice, in `BadgeCode.java` and `badgecode.py`. They must stay
in step, so `benchmark.py` refuses to run if the two implementations disagree on
any sampled code.

## Environment notes

Three things about this specific machine that cost real debugging time, recorded
so they do not cost it twice.

### Tomcat must run on Java 8, not Java 25

Under the Java 25 runtime, `java.nio.channels.Selector.open()` fails on this
machine — every time, reproducibly, outside any sandbox:

```
java.io.IOException: Unable to establish loopback connection
  Caused by: java.net.SocketException: Invalid argument: connect
    at sun.nio.ch.UnixDomainSockets.connect0(Native Method)
```

Tomcat's NIO connector is built on a `Selector`, so the HTTP connector never
starts. The symptom is deceptive: **port 8080 looks like it is listening, but no
request is ever answered.** This is not Tomcat-specific — it breaks any Java NIO
server on this machine, on any Tomcat version.

`scripts/start_tomcat.bat` therefore pins `JAVA_HOME` to the Java 8 JRE, which
uses the older `WindowsSelectorImpl` and works. Java 8 is in any case the runtime
Tomcat 8.5 was built against. `scripts/build.bat` compiles with `--release 8` to
match.

### Apache does not pass `APPDATA` to CGI scripts

`pip install mysql-connector-python` falls back to a **user** install when
`Program Files` is not writable, landing the driver in
`%APPDATA%\Roaming\Python\Python313\site-packages`. mod_cgi hands CGI scripts a
minimal environment that does not include `APPDATA`, so Python cannot locate its
own per-user site-packages and the import fails — even though the identical script
runs perfectly from a shell.

`scripts/deploy.bat` sidesteps this by vendoring the driver into
`C:\xampp\cgi-bin\pylib\`, which `verify.py` adds to `sys.path` explicitly. This
also survives Apache being started as a Windows service under a different account.

### The CGI script needs a space-free shebang

Apache on Windows resolves the CGI interpreter from the script's shebang line, and
the default install path `C:\Program Files\Python313\python.exe` contains a space
that breaks resolution. `scripts/fix_shebang.py` substitutes the 8.3 short form,
`C:/PROGRA~1/Python313/python.exe`, when it deploys the script.

No `httpd.conf` edits are needed for any of this. `C:\xampp\cgi-bin` is already
`ScriptAlias`-ed, and a `ScriptAlias` directory executes every file in it
regardless of extension, so `verify.py` needs no `AddHandler` entry.

## Notes on fairness

The benchmark is only worth something if the two sides are doing the same work.
What is held equal:

- the same SQL, against the same MySQL instance, as the same database user, on a
  unique-indexed column;
- identical response bodies, asserted before timing starts — the run aborts if the
  implementations have drifted apart;
- the same client with the same connection-reuse policy for both, so client-side
  TCP setup is out of the measurement on both sides;
- codes drawn at random from the whole table and rotated, so neither side gets to
  answer one hot row repeatedly;
- a discarded warm-up phase, so the servlet is past class-loading and JIT warm-up
  before anything is recorded.

One caveat stated plainly: the load generator is Python, on the same machine as
the servers. At high concurrency the client itself becomes a limit, which puts a
ceiling on the servlet's measured throughput. **The servlet numbers are therefore
conservative** — the real gap is wider than what is printed.
